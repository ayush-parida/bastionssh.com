By default the server builds each release itself: it installs dependencies and runs the build next to the apps it serves. A Next.js build alone wants 1–2 GB of memory, so on a small server it can be killed halfway (`exit code: 137`). With **build on BastionSSH**, the image is built by a builder running next to BastionSSH and only the finished image travels to the server. The server never runs `npm install` or `next build`; it loads the image and goes through the usual release: health check, zero-downtime switch, rollback if the new release fails.

| | Build on the server (default) | Build on BastionSSH |
| --- | --- | --- |
| `build.where` | `server` | `bastion` |
| Memory the build needs | on the server (1–2 GB free for Next.js) | on BastionSSH's host |
| What reaches the server | the upload, then the build runs there | the image only |
| The upload is kept | with each release on the server | nowhere: removed after the build |
| Rollback | the kept release's image | the same |

Both build the same image from the same upload: the Dockerfile is generated by the same code (Next.js standalone, static, or your own Dockerfile), and Node.js images are pinned the same way.

## Turn it on

For every deploy of an app, set `build.where` in its `bastion.yml` (the **Build on** field of the config form):

```yaml
build:
  type: nextjs
  where: bastion          # server (default) | bastion
```

For one deploy, choose **Build on: BastionSSH** in the Deploy dialog; it starts at what `bastion.yml` says. The choice is greyed out when this BastionSSH has no builder — see [Setting up the builder](#setting-up-the-builder).

Apps with `build.type: image` pull a ready-made image and are not built anywhere.

## What happens

1. The upload stays on BastionSSH's host, in a folder of its own, for the length of the build. It is unpacked with the same checks the server makes (no links leading out, no `..`, no devices, size and entry caps) — and [environment files left out](#environment-files).
2. `NEXT_PUBLIC_*` values, and the names `build.args` lists, are read from the app's `.env` on the server for this build only (see [Build-time values](#build-time-values)).
3. The builder builds the image **for the server's platform** — read from the server's Docker (`linux/amd64`, `linux/arm64`) — with the same Dockerfile a server build would use.
4. The image is streamed, gzipped, straight into the server's Docker over the SSH connection BastionSSH already uses, and tagged `bastion-<app>:<release>`. Nothing partial is ever loaded: a failed or cancelled transfer leaves no image.
5. The upload and its unpacked folder are deleted, whether the build succeeded or not.
6. `bastionctl deploy <app> --prebuilt bastion-<app>:<release>` runs the usual release on the server. `release.json` records `builtOn: bastion`, the platform, the image id and how long the build took; the Releases tab shows it.

The deploy log shows it all as one stream: the build's lines, then the server's. The log panel says where it is — waiting its turn, building, loading the image into the server, deploying.

**Cancel build** in the log panel (operate access) stops the build or the image's transfer; nothing reaches the server. Once the server has the image and deploys it, the deploy runs to its end, as any deploy does.

## Build-time values

Next.js inlines `process.env.NEXT_PUBLIC_*` into the JavaScript **while it builds**. Builds — on the server or on BastionSSH — get every `NEXT_PUBLIC_*` value from the app's `.env` on the server as build arguments, so set them in the **Environment** tab like any other variable and deploy again to change them.

A build gets **nothing else** from `.env` unless you name it in `build.args`:

```yaml
build:
  type: nextjs
  where: bastion
  args: [SENTRY_RELEASE, SENTRY_AUTH_TOKEN]   # besides every NEXT_PUBLIC_*
```

- The values are read over SSH at the start of the build and passed to the builder for that build only. BastionSSH stores none of them.
- They are masked as `••••` in the build log (values of 6 characters or more).
- Generated Dockerfiles declare them with `ARG` in the build stage only, never in the stage that becomes the image — but a value your build writes into its output (as Next does with `NEXT_PUBLIC_*`) is in the image. Only pass what the build needs.
- Your own Dockerfile must declare `ARG NAME` to use one.

## Environment files

Uploads leave out `.env` and every `.env.*` file (`.env.local`, `.env.production`, `apps/web/.env`…) at any depth — except `.env.example`. They tend to hold secrets that would otherwise end up in the release's source on the server and, through `COPY . .`, in the image, where anyone who can pull it reads them. The browser leaves them out when it packs a folder or zip and names them in the Deploy dialog; the server (or BastionSSH's builder) leaves them out of tarballs too, and the build log says which.

Runtime values belong in the app's `.env` on the server; `NEXT_PUBLIC_*` and `build.args` reach the build from there ([above](#build-time-values)).

To deploy them anyway, tick **Include environment files** in the Deploy dialog (it warns first), or run `bastionctl deploy <app> --source app.tar.gz --include-env-files`. This is the same for builds on the server.

## Another CPU architecture

The builder builds for the server's platform. When the server's CPU differs from the builder's — an `amd64` server and BastionSSH on an Apple-silicon Mac or an ARM VM, or the reverse — the image is built under **QEMU emulation**. It works, but it is slower — often several times: a small Next.js app that builds in about 30 seconds natively took about 70 seconds for `linux/amd64` on an Apple-silicon Mac, and `next build` itself three times as long; large apps under QEMU on a Linux host can take 10 minutes or more. The Deploy dialog says so when it applies, and the log names both platforms.

- **Docker Desktop** (Mac, Windows) has QEMU built in: nothing to do.
- **A Linux host** needs QEMU registered once (it lasts until the next reboot; most distributions' `qemu-user-static` / `binfmt-support` packages make it permanent):

  ```sh
  docker run --privileged --rm tonistiigi/binfmt --install all
  ```

  Then restart the builder (`docker compose restart buildkit`) so it sees the new platforms. The Setup line lists the builder's own platform; a deploy to a platform it cannot build for is refused with this command.

To avoid emulation altogether, run BastionSSH on a host of the same architecture as your servers.

## The builder

BastionSSH's builder is the `buildkit` service of its `docker-compose.yml`: a [BuildKit](https://github.com/moby/buildkit) daemon, pinned by digest, that BastionSSH drives with `buildctl` (the same pinned release, in BastionSSH's image).

- **Rootless.** BuildKit runs as an ordinary user in its own user namespace — no `--privileged`, no Docker socket. (Docker's default seccomp and AppArmor profiles would stop it creating that namespace, so the service turns them off for itself.)
- **Its own network**, shared only with BastionSSH. Builds reach the internet (package registries, Docker Hub) and BastionSSH, nothing else — not Redis, not your other containers.
- **Mutual TLS.** A build's `RUN` steps share the builder's network, so without client certificates a project's build script could reach BuildKit's API and drive it. The `buildkit-tls` service makes a CA, a server and a client certificate on the first start (the CA's key is thrown away); only BastionSSH holds the client certificate.
- **One build at a time.** The builder's CPU and memory go to one build; others wait their turn in order and the log says their place. More than `SMT_BUILD_QUEUE_MAX` waiting are refused.
- **Limits.** Memory and CPUs are capped (below); a build (with the image's transfer) is stopped after `SMT_BUILD_TIMEOUT_MS`; an unpacked upload larger than `SMT_BUILD_MAX_CONTEXT_BYTES` is refused.
- **Its cache.** Layers and downloaded packages are cached, so the next build of an app reuses what did not change. The cache is garbage-collected beyond `SMT_BUILDKIT_CACHE_MB`. Nothing else about your apps is kept on BastionSSH's side.

The **Setup** line of a server's Deployments tab shows the builder: reachable or not, its platform and BuildKit version, the cache's size against its limit, and the build running now. Members with **manage** on Deployments get **Clear build cache**, which empties the cache (audited as `deploy.build_cache_clear`); the next build of each app then starts cold. A build running at that moment keeps what it uses.

## Setting up the builder

It is part of the stack: `docker compose up -d` in `deploy/docker` starts `buildkit-tls` (once) and `buildkit` next to `smt` and `redis`. These settings go in `deploy/docker/.env`:

| Variable | Default | What it does |
| --- | --- | --- |
| `SMT_BUILDKIT_ADDR` | `tcp://buildkit:1234` | The builder. Set it empty (`SMT_BUILDKIT_ADDR=`) to turn builds on BastionSSH off; every app then builds on its server. |
| `SMT_BUILDKIT_MEMORY` | `4g` | The builder's memory limit. A Next.js build wants 1–2 GB; raise it for big monorepos. |
| `SMT_BUILDKIT_CPUS` | `2` | The builder's CPU limit. |
| `SMT_BUILDKIT_CACHE_MB` | `10240` | The layer cache is garbage-collected beyond this many MB. |
| `SMT_BUILD_TIMEOUT_MS` | `1800000` (30 min) | A build and its transfer are stopped after this. |
| `SMT_BUILD_MAX_CONTEXT_BYTES` | `1073741824` (1 GiB) | The largest unpacked upload a build takes. |
| `SMT_BUILD_QUEUE_MAX` | `20` | Builds waiting beyond this are refused. |

Run without the builder by setting `SMT_BUILDKIT_ADDR=` and starting only `docker compose up -d smt redis`.

**Certificates** last 10 years. To renew or rotate them, remove both certificate volumes and start the stack again; new ones are made on the way up:

```sh
docker compose stop smt buildkit
docker compose rm -f buildkit buildkit-tls
docker volume rm docker_buildkit-tls docker_buildkit-client-tls   # <project>_buildkit-tls …
docker compose up -d
```

Running BastionSSH without Docker Compose: start a rootless BuildKit yourself, give BastionSSH `SMT_BUILDKIT_ADDR` (`tcp://host:port`) and, for mutual TLS, `SMT_BUILDKIT_TLS_DIR` — a folder with `ca.pem`, `cert.pem` and `key.pem`. `SMT_BUILDCTL_PATH` names the `buildctl` binary when it is not on the `PATH` (the image has it at `/usr/local/bin/buildctl`).

## Permissions and audit

Building on BastionSSH needs exactly what a deploy needs (operate on the server, or manage when `permissions.deploy: manage`). `deploy.start` and `deploy.finish` record `builtOn: bastion`, and `deploy.finish` the platform and how long the wait, the build and the image's transfer took. **Cancel build** is audited as `deploy.build_cancel`, Clear build cache as `deploy.build_cache_clear`.

## When something goes wrong

- **"This BastionSSH has no builder"** — `SMT_BUILDKIT_ADDR` is empty or unset. Set up the builder, or build on the server.
- **"The builder did not answer"** — the `buildkit` service is down or its certificates do not match BastionSSH's. `docker compose ps buildkit` and `docker compose logs buildkit`; after removing only one certificate volume, remove both (above).
- **"The builder cannot build for linux/amd64"** — QEMU is not registered on a Linux host: see [Another CPU architecture](#another-cpu-architecture).
- **`exit code: 137` in a build on BastionSSH** — the builder ran out of memory: raise `SMT_BUILDKIT_MEMORY` and `docker compose up -d buildkit`.
- **"The build did not finish within 30 minutes"** — usually an emulated build of a large app; raise `SMT_BUILD_TIMEOUT_MS`, or build on a host of the server's architecture.
- **A `NEXT_PUBLIC_*` value is missing in the browser** — it was not in the app's `.env` when the build ran (a value in an uploaded `.env.production` is [left out](#environment-files)). Set it in the Environment tab and deploy again.
